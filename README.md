# Wiki Viki

SvelteKit 2 · Svelte 5 · JavaScript · Bun · PostgreSQL/Neon · OpenAI Responses API로 만드는 한국어 업무 위키입니다. 현재 작업의 기준은 [제품 로드맵](docs/product-roadmap-2026-09-21.md), 항목별 완료·미완료는 [판정표](docs/acceptance-matrix.md), 실제 실행 결과는 [구현 기록](docs/implementation-progress.md)입니다.

## 설치와 실행

`.env.example`을 `.env`로 복사하고 전용 개발 DB의 `DATABASE_URL`을 설정합니다. OpenAI 기본 모델은 `gpt-5-mini`이며 `OPENAI_MODEL`로 바꿀 수 있습니다. 키와 연결 문자열은 서버에서만 사용합니다.

같은 DB의 별도 저장 공간을 사용하려면 `.env.local`에 `WIKI_DB_SCHEMA=wiki_development`처럼 **이미 존재하는 스키마**를 지정합니다. 웹 서버와 마이그레이션·계정 생성·시드 명령이 모두 이 설정을 사용합니다. 지정하지 않으면 `public`을 사용하며, 존재하지 않는 이름을 지정해도 다른 스키마로 넘어가지 않습니다. 이 설정은 스키마를 생성하거나 기존 데이터를 이동시키지 않습니다. `wiki_test_*`는 자동 정리되는 검증용이므로 실제 작업 자료를 보관하지 마세요. 서버를 다시 실행해도 같은 설정과 저장된 자료를 사용합니다.

```sh
bun install --frozen-lockfile
bun run migrate
# 첫 운영 계정을 만든 뒤 실행합니다. 아래 계정 절 참고
bun run dev
```

마이그레이션은 파일 순서와 SHA-256 적용 이력을 확인하고 한 트랜잭션에서 실행합니다. 이미 적용한 파일의 체크섬이 다르면 중단합니다. 기존 DB를 사용할 때에는 백업과 이력 호환성을 먼저 확인하고, 체크섬을 바꾸어 검사를 우회하지 마세요. 현재 연결 환경의 이력 불일치와 승인 대기 사항은 구현 기록에 별도로 남겼습니다.

초기 데이터가 필요한 전용 DB에서만 `seed`(안내·초기 파일 초안), `seed:demo`(일반 샘플), `seed:prototype`(업무 예시 문서 6개·체크리스트 초안 1개)을 선택해 실행합니다. 업무 예시 적재의 재실행·사용자 편집 보존은 격리 DB에서 검증했습니다. 실제 DB의 이력 불일치가 해결되기 전에는 마이그레이션과 시드를 실행하지 마세요.

## 구현한 기능

- 게시 문서의 제목·본문·별칭 검색, 분야·태그·상태·기간 필터, 관련도/최근 수정 정렬과 서버 페이지 처리. 일반 검색에 AI 요청이 따라붙지 않습니다.
- 홈의 최근 트렌딩: 실제 검색 실행 기준 최근 1시간 상위 10개 검색어를 30초마다 갱신합니다. 검색어를 누르면 해당 검색 결과로 이동합니다.
- 홈의 최근 시작된 토론: 읽을 수 있는 최근 토론 5건에서 해당 토론과 문서 본문으로 바로 이동합니다. 관리자 모드에서는 문서의 수정 제안·검토/관리와 정기 검토 메뉴 및 직접 조회·저장 요청을 비활성화합니다. 계정 관리는 계속 제공합니다.
- 요청형 AI 설명과 문단별 출처. 최대 6개 게시 문서의 기록된 리비전에서 근거를 골라 설명하며, 근거 부족·취소·키 없음·오류를 구분합니다. 출처는 당시 리비전과 본문 문단으로 연결합니다.
- DOCX·텍스트 PDF·XLSX·PPTX, 파일 최대 10MB·추출 텍스트 12만 자·초안 1–8개. XLSX는 저장된 셀/수식 결과, PPTX는 실제 슬라이드 순서의 텍스트를 읽습니다. OCR·Excel 재계산·원본 레이아웃 복원은 지원하지 않습니다.
- API 키가 없으면 원문 기반 초안과 의미 검사 생략을 표시합니다. 키가 있는 상태의 AI 오류는 자동으로 기본 초안으로 대체하지 않습니다. AI 통합과 AI 검색 설명은 키가 필요합니다.
- 초안 수동 검토·게시, 기존 문서와 AI 통합, 상충 시 새 초안 우선과 상세 이력. 통합안을 만드는 것만으로 게시 문서를 변경하지 않습니다.
- 새 AI 초안과 통합안은 개요를 먼저 작성하도록 요청합니다. 빠진 개요는 생성된 요약이나 본문의 첫 설명 문단으로 보완하며 기존 게시 문서를 일괄 변경하지 않습니다.
- 문서/별칭/리비전의 원자적 저장, 정확한 버전 비교, 충돌 시 입력 보존, 휴지통과 관계 데이터 복구.
- 공통 Markdown 미리보기, 입력 도구/틀/위키 링크 제안, 저장 전 비교, 두 리비전 비교와 되돌리기 전 비교.
- 계정별 수정 제안·승인, 토론 답글·해결, 구독·앱 내 알림, 개인화 동기화, 순서 있는 문서 묶음.
- 담당자·검토 기한·실제 검토 리비전, 보관·읽기 권한, 게시 문서 이름 변경·병합·전체 상태 복원과 메타데이터 비교.
- 읽을 수 있는 현재 문서와 과거 리비전의 Markdown·메타데이터 ZIP 내보내기. 기록되지 않은 과거 메타데이터는 기록 없음으로 구분합니다.
- 라이트/다크, 번호 목차, 모바일 목차, 문단 링크, 글자 크기/읽기 폭, 인쇄, 브라우저 즐겨찾기·최근 문서, 링크·출처 점검과 문서 중심 지도.

## 계정과 운영 접근

기본값은 로그인 필수입니다. 서버 세션은 12시간 유지하며 읽기·편집·검토·운영 역할을 서버에서 검사합니다. 실제 작성자는 세션 계정으로 기록하며 폼의 작성자 이름을 신뢰하지 않습니다. 권한 변경·계정 비활성화·비밀번호 변경은 기존 세션을 종료합니다. 세션 구성은 [SvelteKit의 서버 훅·locals 방식](https://svelte.dev/docs/kit/auth)을 따릅니다.

첫 계정은 마이그레이션한 전용 DB에서 서버 운영자가 생성합니다. 비밀번호는 명령 인자나 저장소에 쓰지 않습니다. 아래는 zsh의 숨김 입력 예시입니다.

```sh
read -s 'WIKI_ACCOUNT_PASSWORD?초기 비밀번호(12자 이상): '
export WIKI_ACCOUNT_PASSWORD
bun run account:create Operator-A admin
unset WIKI_ACCOUNT_PASSWORD
```

이후 `/admin/users`에서 계정을 추가하고 권한을 조정할 수 있습니다. `/account`에서 본인 비밀번호를 변경합니다. 계정 이름은 `Editor-01`, `Operator-07`, `Operator-A` 형식의 작업용 이름입니다.

익명 기능 확인이 필요한 **개발 환경에서만** `WIKI_DEMO_MODE=1 bun run dev`를 사용합니다. 로컬에서 계속 사용하려면 Git에 포함되지 않는 `.env.local`에 `WIKI_DEMO_MODE=1`을 설정합니다. 개발 모드에서는 로그인 화면을 건너뛰며 기존 계정·문서 데이터는 유지됩니다. SvelteKit의 개발 서버에서만 적용되므로 운영 빌드에서는 이 설정이 인증을 해제하지 않습니다. 데모에서는 계정 검토·관리 기능을 활성화하지 않습니다. 연결 DB의 마이그레이션 호환성·실제 배포·남은 품질 검증을 마치기 전까지 사내 운영 준비 완료로 표시하지 않습니다.

개발 모드에서도 계정 관리가 필요하면 `/login?account=1&next=%2Fadmin%2Fusers`에서 실제 운영 계정으로 로그인할 수 있습니다. `handle=Operator-24`처럼 계정 이름을 미리 채울 수 있지만 권한이나 세션을 부여하지는 않습니다. 비밀번호 인증에 성공한 계정의 역할만 적용하며 다른 사용자의 일반 개발 화면은 계속 로그인 없이 열립니다.

개발 중 문서 검사를 완화하려면 `.env.local`에 `WIKI_CONTENT_POLICY=relaxed`를 설정합니다. 이름·직함·연락처·사번·대외비/급여 등의 단어를 자동 차단하지 않고 검토 안내로 남깁니다. AI 의미 기반 보안 검사는 생략하며, 명백한 인증 키·비밀번호 할당·주민등록번호 패턴은 외부 전송 전에 차단합니다. 업로드·수정·게시·통합·검색 답변·임시 복구가 같은 기준을 사용합니다. 생성 결과는 계속 초안이며 게시에는 검토가 필요합니다. 운영 빌드는 이 설정을 무시하고 엄격한 검사를 유지합니다. 자동 회귀 스크립트도 엄격한 정책을 명시하여 로컬 설정의 영향을 받지 않습니다.

## 저장과 복구

트렌딩은 결과가 있는 2–80자 검색어만 집계합니다. 자동완성 입력·검색 결과 새로고침은 집계하지 않으며, 같은 이용자·검색어는 5분 구간당 한 번, 이용자당 최대 20건을 반영합니다. 정규화한 검색어와 검색 결과 문서 ID, 계정 ID 또는 1시간짜리 익명 쿠키의 해시를 저장합니다. IP와 계정 이름은 저장하지 않습니다. 1시간이 지난 이벤트는 집계에서 즉시 제외하고 다음 순위 조회·검색 기록 요청에서 정리합니다. 현재 읽을 수 없는 문서, 보관/삭제 문서, 과거 제한된 범위에서 검색한 내용은 낮은 권한의 순위에 노출하지 않습니다. 개발용 콘텐츠 완화 모드에서도 연락처·인증 정보 등의 검색어는 공유 순위에서 제외합니다.

로그인한 사용자의 편집 입력은 검사 후 계정별 서버 임시 저장으로 최대 24시간 보관합니다. 현재 문서 권한이 있어야 복구할 수 있고, 비밀번호와 게시 승인 체크는 복구하지 않습니다. 익명 개발 데모만 브라우저 임시 저장을 사용합니다. 저장 실패와 버전 충돌에서도 입력을 유지하며 화면에서 직접 복구·삭제할 수 있습니다. 최근 본 문서는 ID와 시각만 30일·최대 30개, 즐겨찾기와 구독은 최대 100개입니다. 로그인하면 계정별로 동기화하며 `/library`에서 본인의 개인화 정보를 지울 수 있습니다.

업로드 작업과 추출 원문 구간은 DB에 기록합니다. `/uploads`에서 같은 작업을 다시 찾고, 동일한 파일·처리 방식의 재요청은 기존 결과를 반환합니다. 실패·중단된 작업은 같은 파일을 다시 선택해 재시도합니다. 파일명과 추출 텍스트는 초안 및 게시 문서의 출처 대조를 위해 보관합니다. 브라우저 요청 종료는 서버 작업 취소나 백그라운드 완료를 보장하지 않습니다. 계정으로 로그인하면 업로드 조회는 해당 계정에 한정됩니다.

3MB를 넘는 파일은 1MB 이하 구간으로 전송합니다. 전송용 바이너리는 계정별 최대 3개 파일을 잠시 보관하고 결합 후 제거합니다. 미완료 전송은 30분 후 만료되며 다음 전송 요청에서 정리합니다. 같은 파일을 다시 선택하면 남은 구간을 이어 보낼 수 있고, 임시 전송 목록에서 직접 지울 수도 있습니다. 원본 파일을 영구 보관하지 않습니다.

## 검증

```sh
bun run test
bun run check
bun run build
bun run test:database
bun run test:integration
bun run test:auth
```

앞의 세 명령은 로컬 단위 검사·Svelte 검사·빌드입니다. DB/HTTP 검증은 `.env`의 DB에 별도 `wiki_test_*` 스키마를 만들고, 매 트랜잭션에 `SET LOCAL search_path`와 스키마 확인을 적용합니다. 테스트 종료 시 해당 테스트 스키마만 제거합니다. DB 계정에는 스키마 생성 권한이 필요합니다. 기존 `verify-prototype.js`는 현재의 버전 보호/격리 계약을 따르지 않으므로 실행하지 않습니다.

사용자 자료가 생긴 임시 시연 스키마는 `node --env-file=.env scripts/promote-development-schema.js --from=wiki_test_... --to=wiki_development`로 사전 검사할 수 있습니다. 해당 서버와 진행 중인 업로드를 먼저 종료한 후 같은 명령에 `--execute`를 추가하면 전체 행 보존을 확인하며 이름만 바꿉니다. 이후 `.env.local`의 `WIKI_DB_SCHEMA`를 새 이름으로 지정하고 일반 개발 서버를 실행합니다. 원본 public으로의 병합·이동은 수행하지 않습니다.

`bun run test:schema`는 별도로 만든 두 스키마에서 영구 설정과 테스트 설정의 격리, 풀러를 통한 반복 요청, 트랜잭션 롤백, 없는 스키마의 거절을 검사한 뒤 검사에 사용한 스키마만 정리합니다. 테스트 설정은 `.env.local`의 영구 설정보다 우선하며 운영 모드에서는 테스트 스키마 사용을 거절합니다.

`bun run test:legacy-rehearsal`은 현재 연결 DB의 다른 마이그레이션 계열에 대한 호환 검증입니다. 원본 테이블·함수·뷰·트리거를 같은 DB의 독립된 복사본에 준비하고, 기존 값·주소·이력 보존과 새 저장 함수를 검사합니다. 성공해도 전체 트랜잭션을 롤백하므로 원본 적용이나 서버 전환 명령이 아닙니다. 현재 비어 있는 계정·업로드·협업 영역에 데이터가 생기면 추가 매핑 없이 계속하지 않습니다. [적용 경로와 제한](docs/deployment-handoff.md)을 확인하세요.

기존 계열 DB의 적용 전 검사는 `bun run migrate:legacy --schema=public`입니다. 실제 적용은 기존 앱의 쓰기를 중지한 뒤 `--apply --writers-stopped`를 추가합니다. 지정한 스키마의 독립 보존본을 만들고, 기존 열·자료·이력·별칭을 대조한 뒤 하나의 트랜잭션으로 적용합니다. 실패하면 모두 롤백합니다. 성공 기록과 보존본 이름은 대상 스키마의 `wv_legacy_upgrade`에 남으며, 반복 실행은 기존 보존본을 유지하고 새 마이그레이션만 확인합니다. 이 명령은 개발 스키마를 public에 합치거나 자동으로 배포하지 않습니다.

실제 AI 검증은 별도로, 합성 입력만 사용하며 API 사용량이 발생합니다.

```sh
bun run test:ai-merge
node --env-file=.env scripts/verify-ai-answer.js
bun run test:ai-workflow
```

`test:ai-workflow`는 합성 원문과 생성물을 임시 검토 파일에 기록하고 멈춥니다. 검토 후 터미널에 `reviewed`를 입력해야 게시·통합 검증을 이어갑니다. 실제 사용자 자료를 가져오거나 게시하지 않습니다.

`bun run test:integration --transfers-only`는 분할 전송을, `--benchmark`는 전체 회귀 후 로그인 검색 60회를 측정합니다. `bun run test:auth --ui`는 대화형 터미널에서만 실행하며 Enter로 격리 미리보기와 테스트 자료를 정리합니다. UI 미리보기에서는 설정된 AI 키를 사용해 실제 의미별 초안 생성을 제공하며, 일반 인증 검증은 AI를 사용하지 않습니다. 미리보기를 유지하면서 인증 검증을 실행하려면 `bun run test:auth --recovery --port=5187`처럼 다른 포트를 지정합니다. 사용 중인 포트에서는 시작하지 않습니다.

정확한 통과·생략·미검증 결과와 UI 크기/테마, 실제 AI 호출 사용량은 구현 기록을 확인하세요. 검색 성능 목표나 실제 배포 성공을 로컬 빌드 통과로 대신하지 않습니다.

## Vercel

기존 `@sveltejs/adapter-vercel`과 Node.js 22 배포 설정을 유지합니다. Install Command는 `bun install --frozen-lockfile`, Build Command는 `bun run build`입니다. `DATABASE_URL`, 필요하면 `OPENAI_API_KEY`·`OPENAI_MODEL`을 서버 환경 변수로 설정합니다. 마이그레이션과 시드는 빌드 중 자동 실행하지 않습니다.

[Vercel Functions 요청 크기 제한 4.5MB](https://vercel.com/docs/errors/function_payload_too_large)에 맞춰 큰 파일은 1MB 구간으로 보냅니다. 로컬 HTTP와 실제 Neon에서 9,962,971바이트 DOCX의 10구간 전송·재개·변조/권한 검사·초안 생성을 확인했습니다. 실제 Vercel 배포와 Node22에서의 10MB 파일·처리 시간 검증은 별도로 남아 있습니다.
