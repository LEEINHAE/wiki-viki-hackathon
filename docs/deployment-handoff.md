# DB 연결과 배포 전환 상태

2026-09-21 사용자가 전달한 Neon DB를 적용 대상으로 확정했다. 전달된 연결 정보는 기존의 Git 제외된 `.env` 설정과 같으며 실제 연결에 성공했다. 연결 환경을 다시 읽기 전용으로 확인했다. 조회 결과는 [DB 호환성 원자료](database-compatibility.json)에 있으며 접속 문자열·비밀번호·사용자 본문은 포함하지 않는다.

## 확인한 현재 상태

- 연결 DB의 public에는 13개 마이그레이션이 있다. 현재 조회에서 `001_initial.sql` 체크섬은 로컬과 **일치**한다. 이전 점검의 체크섬 불일치 기록과 구분한다.
- 나머지 12개는 `002_safe_editing.sql`부터 `013_document_tags.sql`까지 다른 구현 계열이다. 이 체크아웃의 `002_prototype_features.sql`–`025_search_trending.sql` 적용 이력은 없다.
- 기존 DB의 `users`, `sessions`, `upload_jobs`, `document_sources`, `collections` 등은 새 코드의 `wv_*` 테이블과 다른 구조다. 최신 행 수 조회에서는 계정·개인화·업로드·협업 테이블이 비어 있었지만, 적용 시점에 데이터가 생겼다면 계정·개인 목록·원문 연결의 별도 변환이 필요하다.
- 문서에는 `owner_id`, `reviewed_at`, `reviewed_by`, `next_review_at`, `merged_into`, `governance` 등이 이미 있다. 기존 리비전은 `snapshot`에 상태를 보관한다. 이 값을 검토 없이 새 기본값으로 대체하지 않는다.
- 배포 빌드 산출물은 `nodejs22.x` 런타임과 스트리밍 응답을 설정한다. `.vercel`에는 빌드 산출물만 있고 연결된 프로젝트 설정은 없다. 현재 실행 환경에 `VERCEL_TOKEN`, `VERCEL_PROJECT_ID`, `VERCEL_ORG_ID`, `NEON_API_KEY`는 설정되어 있지 않고 Vercel CLI도 설치되어 있지 않다. 사용자가 해당 서비스 계정을 가지고 있지 않다는 뜻은 아니다.
- 개발용 `http://127.0.0.1:5185` 서버는 같은 DB의 영구 개발 스키마 `wiki_development`를 사용한다. 이전 테스트 저장 공간을 자료 변경 없이 전환했으며 `.env.local`의 `WIKI_DB_SCHEMA`로 재시작 후에도 유지한다. 사용자의 최신 요청으로 로그인 없이 이용할 수 있으며 public 전환이나 실제 배포를 대신하지 않는다.

## 확정한 적용 경로와 남은 연결 정보

사용자가 현재 Neon DB를 지정했으므로 **현재 DB와 호환되는 업그레이드** 경로를 사용한다. 별도 DB 선택을 다시 요청할 필요는 없다. 기존 13개 이력과 체크섬, 문서·별칭·리비전 ID, 계정·업로드·출처 관계를 유지해야 한다.

현재 개발 화면의 자료도 같은 DB의 별도 스키마에 있으므로 그대로 보존한다. 전달된 URL로 연결 설정은 확인했지만 public 스키마 전환이나 배포를 수행한 것으로 간주하지 않는다. 최신 조회에서는 public 문서 42개·초안 52개·리비전 63개로 이전 검사 후 자료가 추가됐으므로, 이전 복사본만 근거로 원본 전환을 실행하지 않는다.

사용자가 기존 GitHub 연동을 사용하며 별도 Vercel 연결이 필요 없다고 명시했다. 추가 프로젝트 연결 작업과 연결 정보 요청은 제외한다. 원본 DB 업그레이드는 기존 쓰기를 중지하는 전환 구간과 백업을 준비한 뒤 적용해야 한다. 기존 이력의 체크섬을 덮어쓰거나 이력 행을 지워서 통과시키지 않는다.

## 복사본 검증에서 다루는 호환 차이

최종 `bun run test:legacy-rehearsal`은 실제 Neon 복사본에서 통과했고 전체 롤백을 확인했다([검증 결과](legacy-upgrade-rehearsal.json)). 아래 대응은 복사본에서 확인한 전환안이며 실제 DB 적용을 완료한 것이 아니다.

- 사용자 지정 DB로 다시 검증한 원본에는 문서 42개·초안 52개·별칭 81개·리비전 63개가 있다. 과거 메타데이터 `snapshot`이 있는 리비전과 없는 리비전을 구분해 보존했다. 없는 메타데이터를 현재 값으로 채워 과거 기록처럼 만들지 않는다.
- `revisions.actor_id`와 `discussions.status`는 새 마이그레이션과 열 이름이 겹친다. 복사본에서 원래 열을 `legacy_*`로 보존한 뒤 새 열을 준비한다. 기존 마이그레이션 이력과 체크섬은 유지한다.
- 기존 문서에는 이전 `category`에 분류가 있지만 `field`에는 반영되지 않은 경우가 있다. 검증에서는 업무 절차→절차, 위키 안내/일반 지식→일반으로 연결하되 원래 `category`와 `field`를 보존한다. 실제 적용 전 분류 대응도 함께 검토한다.
- 기존 저장용 트리거 8개와 새 트리거를 동시에 실행하면 과거 코드의 저장 규칙도 실행된다. 복사본에서는 함수·뷰·트리거 정의를 보존하고 기존 트리거만 중지한 뒤 새 저장 함수를 확인한다. 실제 전환에는 기존 앱의 쓰기 중지가 필요하다.
- 과거 스냅샷은 별칭·제목·분류·자료명 등을 읽을 수 있도록 변환하지만 당시 출처 관계가 기록되지 않았으므로 완전한 v3 상태 복원으로 표시하지 않는다. 원래 `snapshot`은 그대로 보존한다.
- `test:legacy-rehearsal`은 성공 여부와 관계없이 복사본을 포함한 트랜잭션을 롤백한다. serial 기본값과 외래 키가 원본 스키마를 가리키지 않게 분리하며 원본 문서·계정·시퀀스를 갱신하지 않는다. 범용 운영 마이그레이션이나 전환 승인을 대신하는 명령이 아니다.

## 실제 적용 명령

- `bun run migrate:legacy --schema=public`: 읽기 전용으로 현재 자료와 지원 가능한 변환 범위를 점검한다.
- `bun run migrate:legacy --schema=public --apply --writers-stopped`: 기존 앱의 쓰기를 중지한 뒤 실행한다. 대상 테이블을 잠그고 독립된 `wiki_backup_legacy_*` 보존본에 모든 원래 행과 시퀀스·함수·뷰·트리거를 보관한 후 새 구조를 적용한다. 비교 실패 시 트랜잭션 전체가 롤백된다.
- 성공 기록은 대상의 `wv_legacy_upgrade`에 보존본 이름과 함께 저장된다. 다시 실행하면 같은 보존본을 유지하며 아직 적용되지 않은 마이그레이션만 확인한다. 커밋 직후 터미널이 끊겨도 DB 기록으로 완료 여부를 확인할 수 있다.
- 백업 이후 새 데이터가 생긴 경우에는 보존본으로 단순 교체하지 않는다. 복원 시점 이후 자료를 함께 보존하는 별도 복구 절차가 필요하다.

공유한 실제 적용 함수를 독립된 원본 복사본에서 실행해 보존본 생성·전환·전체 행 대조·반복 실행·새 문서 저장까지 통과했다. 성공 후 복사본과 보존본 모두 롤백했다. 실제 public에는 여전히 적용하지 않았다. 사용자용 개발 서버는 같은 DB의 `wiki_development`를 계속 사용한다.

2026-09-22 사용자가 이 Neon DB를 사용하는 서비스는 이 위키뿐이라고 확인했다. 다른 서비스의 데이터 사용 여부는 해결됐으며 다시 질문하지 않는다. DB 통합 검증도 사용자 요청으로 생략한다. 별도 Vercel 연결 작업은 하지 않는다.

- 독립된 후보 디렉터리에서 잠금 파일 기반 의존성 설치, 단위 검사 30개 통과·선택 DB 검사 1개 생략, Svelte 오류/경고 0, Vercel Node22 빌드 패키징 성공을 확인했다. 사용자 요청대로 DB 통합 검증은 다시 실행하지 않았다.

- 코드 기준 선택과 실제 자료 선택을 구분한다. 사용자에게 모두 보존하며 중복 문서에 개발본을 적용할지, 기존 웹사이트 자료를 사용할지, 개발 자료를 사용할지 질문한 상태다. 답변 전 자료 병합·원본 전환·운영 배포는 수행하지 않는다. 양쪽 스키마의 모든 현재 자료를 유지한다.

## 적용 후 남은 확인

1. 선택한 DB의 기존 데이터·계정·URL·리비전·출처 연결을 업그레이드 전후 대조한다.
2. 기존 GitHub 연동을 유지한다. 사용자 요청에 따라 별도의 Vercel 프로젝트 연결은 수행하지 않는다.
3. 배포된 Node22에서 로그인·검색·10MB 분할 전송·AI 처리/시간 초과/재조회·권한 변경을 확인한다. 로컬 p95 430.44ms와 실제 배포 성능·콜드 스타트는 구분한다.
4. 200% 확대와 처음 사용하는 사람의 10문항 탐색 실험은 [사용성 기록지](usability-protocol.md) 및 [항목별 판정표](acceptance-matrix.md)에 실제 결과를 기록한다.

최초 테스트의 public 문서 ID95와 리비전 ID125–143 정리는 이 업그레이드와 별개의 승인 대기 사항이다. 기존 문서들의 이력에 걸친 삭제라는 이유로 자동 승인 검토가 거절했다. 명시적 승인 전에는 삭제하지 않는다.
