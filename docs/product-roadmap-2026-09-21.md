# Wiki Viki — 제품 목표·디자인 기준·실행 로드맵

> 기준일: 2026-09-21. 이 문서는 Wiki Viki의 구현 목표를 독립적으로 정의한다. 기존 기술 스택과 업무 기능을 보존하면서, 고딕체·중립적인 읽기 화면·일관된 작업 흐름을 적용하고 검색·작성·검토·운영 기능을 단계적으로 완성한다.

## 0. 실행 목표와 판단 기준

**이 문서에 명시된 기능·디자인·데이터·품질 요구를 구현하고 검증한다.** 요구사항의 의미와 완료 조건은 본문에 직접 정의한다. 작업을 시작할 때 실제 구현 상태를 확인하고, 이미 충족한 항목은 보존하며 미완료 항목을 P0 → P1 → P2 순서로 진행한다.

- **보존할 기능:** 실제 문서 검색, 다중 문서 기반 AI 답변, 네 가지 파일 형식의 용어별 초안 생성, 새 게시와 AI 통합, 상충 상세 역사, 수정 충돌 보호, 예시 데이터와 문서 연결.
- **우선할 디자인:** 업무 화면의 고딕체, 긴 문서의 계층형 목차·문단 번호·구분선, 중립적인 본문 배경, 높은 정보 밀도, 일관된 버튼·상태·입력 스타일. 베이지·오렌지·올리브 브랜드 색은 유지한다.
- **변경 경계:** SvelteKit·Svelte·JavaScript·Bun·PostgreSQL/Neon·OpenAI·Vercel 구성을 유지한다. 기존 문서 URL·별칭·이력·사용자 데이터를 보존하며 필요한 데이터 확장은 점진적으로 적용한다.
- **상태 해석:** “현재”, “미구현”, 완료 체크는 기준일의 출발 상태다. 현행 제약을 영구 유지하라는 뜻이 아니다. 명시된 개선 목표와 현행 동작이 다르면 개선 목표를 최종 동작으로 적용한다.
- **완료 판단:** 실제 코드와 실행 결과로 확인한 항목만 완료로 표시한다. 과거의 확인 결과나 문서에 적힌 완료 표시를 새 검증의 증거로 대신하지 않는다.
- **의사 결정:** 구현 방법은 기존 구조 안에서 정한다. 요구의 의미가 모호하거나 데이터 보존·사용자 동작에 영향을 주는 선택이 해결되지 않으면 사용자에게 질문한다.

| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 시각 체계        | 장식적인 제목과 큰 카드 중심 구성을 고딕체·중립적인 읽기 면·명확한 구분선·작업 중심 정보 배치로 개선한다.                                   |

| 삭제             | 현재의 영구 삭제를 P0에서 복구 가능한 휴지통으로 바꾸고 관계 데이터도 복원한다.                                                             |

| 개인화와 운영    | 익명 식별자와 인증을 구분한다. 브라우저 개인화는 P1, 계정 기반 협업은 P2로 진행하되 기본 인증·권한은 실제 사내 운영 전에 완료한다.          |

## 1. 제품 목표와 확정된 방향

흩어진 업무 문서와 사내 지식을 검색하고 연결하며 함께 개선하는 한국어 사내 위키를 제공한다. 핵심 문구는 **“모르는 것은 5초 안에, 아는 것은 5분 안에.”**이다. 이는 사용 경험의 방향을 나타내며 AI 응답 시간 보장은 아니다.

검색·문서 읽기·작성·검토를 중심에 두고 베이지·오렌지·올리브의 브랜드 정체성을 유지한다. 업무 화면은 고딕체·중립적인 배경·명확한 제목 계층과 구분선으로 구성한다. **기존 기술 스택을 변경하지 않는다.**

필수 동작은 다음과 같다.

- 검색 첫 설명은 고정 예시가 아니라 **여러 실제 게시 문서를 바탕으로 AI가 생성한 답변**이다.
- 파일 하나를 **용어·개념·업무 절차별 여러 초안**으로 나눈다. 단일 주제면 하나만 만들 수 있으며 최대 8개다.
- 예시 문서를 실제 DB에 적재해 검색·읽기·연결·초안 검토에서 사용할 수 있게 한다.
- AI 위키파이어는 DOCX·텍스트 PDF뿐 아니라 **XLSX·PPTX**도 지원한다.
- 위키파이어 모달의 스크롤바는 둥근 프레임 안에 있고, **닫기(X)는 본문을 스크롤해도 계속 보인다.**
- 초안은 새 문서로 게시하거나 기존 문서와 AI 통합할 수 있다. **상충하면 새 초안을 우선하고, 문서 역사에 기존 내용과 새 초안 내용을 별도로 기록한다.**
- AI 생성물은 검토 후 명시적으로 게시·통합한다. 자동 게시하지 않는다.

사용 흐름은 다음 세 가지다.

1. **검색 → 일반 검색 결과 및 AI 설명 → 출처 문서 → 관련 문서·역링크 탐색**
2. **자료 업로드 → 텍스트 추출·검사·용어별 초안 생성 → 검토·수정 → 새 문서 게시 또는 기존 문서와 AI 통합 → 역사 확인**
3. **문서 직접 작성·편집 → 리비전 기록 → 토론·변경 비교·이전 본문으로 되돌리기**

구성원·편집자·운영 담당자는 이용 목적의 구분이다. 현재 인증 기반 계정·역할·접근 권한 구분은 없다. 익명 편집자 배지를 로그인 상태로 표현하지 않는다.

제품의 중심은 문서 전환뿐 아니라 구성원이 매일 지식을 활용하는 경험이다.

- **찾기:** 약어·별칭·업무 용어로 필요한 문서와 근거 문단에 도달한다.
- **읽기:** 긴 문서의 제목 계층과 목차를 파악하고 모바일에서도 읽기 편하게 한다.
- **신뢰하기:** 원문 출처, 실제 검토 여부, 변경 이력과 적용 시점을 구분한다.
- **기여하기:** 작은 수정부터 파일 전환까지 작업을 잃지 않고 검토·게시를 끝낸다.

현재 사용자 흐름을 유지하면서 분야 탐색·즐겨찾기, 편집 미리보기·변경 비교, 원문 대조·정기 검토를 단계적으로 추가한다. 분야·개인화·편집·출처 대조는 P1까지, 인증 기반 검토 주기는 P2에서 완성할 목표다.

## 2. 유지할 기술 스택과 데이터 전달 구조

| 영역                      | 현재 기준                                                                                    |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| UI·서버                   | SvelteKit 2, Svelte 5 runes, JavaScript, Vite                                                |
| 개발·패키지·스크립트 실행 | Bun, 기존 실행 명령·의존성 버전 잠금 유지                                                    |
| 저장소                    | PostgreSQL / Neon. 웹 서버는 `@neondatabase/serverless`, 마이그레이션·시드는 `postgres` 사용 |
| AI                        | 기존 `openai` SDK와 OpenAI Responses API. 기본 모델 `gpt-5-mini`, `OPENAI_MODEL`로 선택      |
| 문서 렌더링·비교          | `marked`, `diff`, 기존 위키 링크·각주 처리                                                   |
| 파일 추출                 | DOCX: `mammoth`; PDF: `pdf-parse`; XLSX: `read-excel-file`; PPTX: `jszip` + `@xmldom/xmldom` |
| 스타일·아이콘             | CSS 변수 기반 전역 스타일, Svelte 컴포넌트 스타일, 로컬 WOFF2 글꼴, SVG 아이콘               |
| 배포                      | `@sveltejs/adapter-vercel`, 서버 Node.js 22, 기존 Vite·SvelteKit 배포 구성                   |

- DB 연결 정보와 AI 키는 서버 환경 변수 `DATABASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL`로 관리한다. 클라이언트나 문서에 실제 키를 기록하지 않는다.
- 최초 페이지는 SvelteKit 서버 렌더링을 사용하고, 내부 이동 시 프레임워크가 직렬화된 페이지 데이터를 받아 화면을 갱신한다. 네트워크의 JSON·배열 형태 응답은 이 데이터 전달 방식이다. 응답 형식 자체를 바꾸기보다 필요한 데이터만 조회하고 렌더링하는 방식으로 성능을 개선한다.
- 자동완성·검색 답변·파일 업로드는 각각 기존 JSON API를 사용한다. 폼 저장·게시·통합은 SvelteKit 서버 액션을 사용한다.
- 일반 검색 결과와 AI 설명 요청을 분리해, AI 생성이 지연되거나 실패해도 원문 검색 결과를 이용할 수 있게 한다. 현재 AI 답변은 완료 후 표시하며 스트리밍은 구현하지 않았다.
- 별도 프런트엔드 프레임워크, UI 프레임워크, AI 제공자, 벡터 DB를 도입하는 것으로 현재 구성을 대체하지 않는다.

확장은 기존 라우트·서버 `load`·form actions·API와 공통 컴포넌트를 사용한다. 검색은 SQL·실행 계획·인덱스를 먼저 개선하고, AI는 기존 연동을 재사용해 출처·실패 처리·요청량 관리를 강화한다. 편집 미리보기와 게시 화면의 렌더링 규칙을 공유한다.

새 라이브러리는 기존 도구로 해결하기 어려운 구체적 요구가 있을 때만 추가한다. 기본 계획에 React/Next.js 전환, 전면 TypeScript 전환, 대형 UI 프레임워크, 별도 검색 서버·벡터 DB·Redis·마이크로서비스를 포함하지 않는다. 데이터 확장은 기존 문서·초안·별칭·이력을 보존하는 마이그레이션으로 진행한다.

## 3. 현재 화면 구조와 탐색 — 기능 보존 기준

| 주소·진입점                  | 유지할 화면과 동작                                                             |
| ---------------------------- | ------------------------------------------------------------------------------ |
| `/`, `/?view=search`         | 검색 우선 홈, 핵심 문구·검색창, 연결이 많은 용어, 실제 통계, 자료 업로드 안내  |
| `/?view=activity`            | 활동 대시보드: 최근 변경, 검토 대기 초안, 연결 순위, 주요 공지, 최근 토론      |
| `/?view=map`                 | 실제 위키 링크 기반 지식 지도, 역링크 순위, 아직 작성되지 않은 연결 대상       |
| `/?q=검색어`                 | AI 설명·문단별 출처, 일반 검색 결과, 분야 필터, 새 문서 작성·자료 업로드 진입  |
| `/wiki/[slug]`               | 문서 본문, 분야·수정 정보·별칭, 목차, 관련 문서·역링크, 편집·역사·토론         |
| `/edit/[slug]`               | 문서 생성·편집, 별칭·편집자·요약 입력, 기존 문서 삭제                          |
| `/history/[slug]`            | 본문 리비전, 변경 비교, AI 통합·상충 이력, 이전 본문으로 되돌리기              |
| `/discussion/[slug]`         | 문서별 토론 목록·새 토론 등록                                                  |
| `/wikify` 및 위키파이어 모달 | 동일한 업로드·초안 생성 컴포넌트를 공유하는 독립 페이지와 모달                 |
| `/drafts`, `/drafts?open=ID` | 초안 상태별 목록, 수정·미리보기, 같은 업로드의 초안 이동, 새 게시·AI 통합·삭제 |

공통 헤더는 W 원형 마크와 “위키비키”, 최근 변경·AI 위키파이어·초안 검토 메뉴, 필요한 화면의 소형 검색창, 테마 전환, 익명 편집자 표시를 유지한다. 본문 바로가기와 이용 원칙·도움말 푸터를 제공한다.

### 홈·활동·지식 지도

- 통계는 게시 문서 수, 서울 시간 기준 이번 주 리비전 수, 문서 간 연결 수, 미게시 초안 수다. “검토 대기 초안” 수에는 `review`와 `blocked`가 함께 포함된다.
- 최근 변경은 최근 수정된 문서 최대 12개다. 공지는 최신 4개, 최근 토론은 최신 5개를 표시한다.
- 순위와 “연결이 많은 용어”는 실제 역링크 수 기준이며 조회수·인기도·방문 이력으로 표현하지 않는다.
- 그래프는 별칭을 대표 문서로 해석하고, 자기 자신을 가리키는 링크 및 같은 문서 사이의 반복 링크를 제외한다.
- 지도는 역링크가 가장 많은 중심 문서와 연결된 이웃 최대 6개를 표시한다. 전체 문서 그래프나 드래그 편집 도구는 아니다.
- DB 오류는 안내와 빈 상태로 표시한다. 예시 수치나 가짜 콘텐츠로 오류를 감추지 않는다.

### 검색과 AI 설명

- 제목·본문·별칭을 PostgreSQL 키워드 검색으로 찾는다. 제목 완전 일치와 제목·별칭의 일치에 더 높은 가중치를 주고, 관련도·최신 수정 순으로 최대 40개를 표시한다.
- 검색어는 최대 200자다. 한국어 조사·일반 질문 표현을 정리하고 다중 검색어를 처리한다.
- 자동완성은 200ms 입력 지연 후 최대 5개를 표시한다. 위·아래 방향키, Enter, Escape를 지원하며 이전 요청을 취소해 오래된 결과가 최신 입력을 덮지 않게 한다.
- 분야는 제목 규칙으로 분류한다: 위키 안내, 유틸리티, 안전, 업무 절차, 설비, 공정, 일반 지식. 현재 별도 분류 테이블이나 사용자가 편집하는 태그 체계가 아니다.
- AI는 상위 검색 문서 최대 6개에서 관련 본문을 추려 1–3개 문단의 설명을 만들도록 요청한다. 전체 DB를 읽거나 모든 검색 결과를 인용하는 방식은 아니다.
- 구조화된 답변의 출처 ID를 서버에서 검증하고, 문단별 인용 번호와 실제 문서 링크를 표시한다. 초안은 검색 답변의 근거에 포함하지 않는다.
- 관련 원문이 없거나 근거가 부족하면 그 상태를 알린다. 키 없음·한도 초과·연결 실패 시 일반 검색 결과를 유지하고, 사용 불가 상태에는 다시 시도를 제공한다.
- AI 실패를 고정된 예시 답변으로 대체하지 않는다. 검색 답변·초안 생성·문서 통합 프롬프트는 자료 안의 명령을 실행할 지시로 취급하지 않는다.

### 문서 읽기·편집·역사·토론

- Markdown 제목·표·목록·인용·코드·취소선, 각주, `[[문서]]`, `[[문서|표시 이름]]`을 지원한다. 원시 HTML은 이스케이프하고 링크 주소를 제한한다.
- 제목별 앵커와 계층형 목차, 목차 접기·펼치기를 유지한다. 별칭으로 열면 대표 문서 내용과 별칭 안내를 표시한다.
- 관련 문서는 본문에서 나가는 링크, 역링크는 이 문서를 가리키는 실제 링크로 계산한다. 제목 일부가 같은 문서를 임의의 역링크로 취급하지 않는다.
- 없는 문서는 작성 안내로 연결한다. 같은 슬러그의 미게시 초안이 있으면 초안 검토 진입을 제공한다.
- 직접 편집에서 제목·본문·쉼표로 구분한 별칭·익명 편집자·변경 요약을 입력한다. 본문 저장과 새 리비전 기록을 함께 처리한다.
- 역사에는 시각·편집자·요약, 이전 리비전과의 줄 단위 차이를 표시한다. 되돌리기도 새 리비전을 만들며 기존 이력을 지우지 않는다.
- 문서 삭제는 확인창을 거친다. 삭제 시 해당 문서의 리비전·토론·별칭도 DB 외래 키 규칙에 따라 삭제되며 휴지통은 없다.
- 토론은 문서별 주제·의견·익명 작성자·시각을 기록하는 목록이다. 답글 트리·실시간 채팅·승인 워크플로는 현재 없다.

## 4. AI 위키파이어와 파일 지원

### 업로드·생성·검토 흐름

1. 파일 하나를 선택하거나 드래그하고 익명 편집자 이름을 입력한다.
2. 클라이언트와 서버에서 빈 파일·확장자·최대 10MB 용량을 검사한다.
3. 텍스트를 추출하고 원문의 정규식·의미 기반 검사를 수행한다. 검출 내용은 생성 후 초안 상태와 사유에 반영한다.
4. AI가 제목·섹션·관련 링크·별칭을 포함한 용어별 초안 1–8개를 생성한다. 불확실한 내용은 `[검토 필요]`로 표시하도록 지시한다.
5. 결과 구조, 비어 있는 제목, 중복 슬러그와 생성 본문의 정규식 검사를 확인한다. 기존 문서 및 함께 생성한 초안에 관련 용어를 연결한다.
6. 같은 업로드의 여러 초안을 한 트랜잭션으로 저장한다. 결과 목록에 각 제목·상태·링크 수와 검토 화면 진입을 제공한다.
7. 각 초안을 검토·수정한 다음 개별적으로 새 게시 또는 AI 통합한다.

업로드·생성·검토의 3단계 표시, 처리 중 중복 제출 방지, 성공·실패·한도 초과·텍스트 없음 안내를 유지한다. 브라우저 요청이 120초를 넘으면 초안 목록을 먼저 확인하도록 안내한다. 요청 종료나 모달 닫기가 서버 작업의 취소·롤백을 보장하지는 않는다.

| 형식 | 추출 기준                                                                 | 현재 지원하지 않는 범위                     |
| ---- | ------------------------------------------------------------------------- | ------------------------------------------- |
| DOCX | 본문 텍스트                                                               | 업로드 자료의 레이아웃·서식 재현            |
| PDF  | 텍스트 기반 PDF의 텍스트                                                  | 스캔 PDF·이미지 OCR                         |
| XLSX | 파일에 기록된 시트 순서, 시트 이름·셀 값·빈 열 위치·날짜·저장된 수식 결과 | 수식 재계산, 서식·차트·이미지 복원          |
| PPTX | 프레젠테이션의 실제 슬라이드 순서, 텍스트 런·줄바꿈·표의 텍스트           | 발표자 노트, 이미지 OCR, 도형·레이아웃 복원 |

- 구형 `.xls`·`.ppt`는 `.xlsx`·`.pptx`로 다시 저장한 뒤 업로드한다. CSV·이미지·암호 파일은 현재 지원 범위가 아니다.
- 글자가 없는 시트·슬라이드만으로 가짜 본문을 만들지 않는다. 읽을 수 없는 파일은 추출 오류로 안내한다.
- API 키가 없으면 원문 기반 기본 초안 하나를 만들고 `aiGenerated=false`와 의미 검사 생략을 표시한다. 키가 있는 상태의 API 오류를 기본 초안으로 조용히 대체하지 않는다.

### 모달 유지 조건

- 네이티브 `dialog`, 어두운 반투명·블러 배경, 둥근 패널을 유지한다.
- 프레임은 `overflow: hidden`, 내부 본문만 세로 스크롤한다. 스크롤바는 패널 안쪽 여백에 놓인다.
- 닫기(X)는 스크롤 본문과 분리된 상단 영역에 둔다. 긴 업로드 결과에서도 계속 클릭할 수 있어야 한다.
- 모달이 열린 동안 뒤 페이지의 스크롤을 막고 내부 스크롤의 전달을 제한한다.
- X·배경 클릭·Escape로 닫고, 페이지 이동 후에도 모달을 정리한다.
- 데스크톱 최대 폭 680px, 최대 높이 90dvh를 기준으로 하며 작은 화면에서는 좌우 여백과 최대 높이 94dvh를 적용한다.

## 5. 초안 게시와 기존 문서 AI 통합

### 초안 검토

- 미게시 초안을 전체·검토 대기(`review`)·확인 필요(`blocked`)로 필터링한다. `published`는 검토 목록에서 제외한다.
- 업로드 파일명·생성일·검토자·검사 사유, 같은 업로드의 다른 초안으로 이동, 내용 수정과 **저장된 초안** 미리보기를 제공한다.
- 초안 수정 후 먼저 저장해야 게시·통합할 수 있다. 저장되지 않은 수정은 미리보기에 반영되지 않음을 알린다.
- 수정 저장 시 다시 검사해 `review` 또는 `blocked`를 갱신한다. 기존 AI 통합안은 초안 수정 저장 시 초기화한다.
- 초안 삭제는 확인창과 버전 검사를 거치며 미게시 초안만 삭제한다.

### 새 문서 게시

- 게시 직전 제목·본문의 정규식·의미 기반 검사를 다시 수행한다.
- 같은 제목·슬러그의 기존 문서 또는 해당 슬러그의 별칭이 있으면 새 게시를 막고 AI 통합이나 제목 변경을 안내한다. **초안 게시로 기존 문서를 암묵적으로 덮어쓰지 않는다.**
- 문서 생성·최초 리비전·초안의 게시 완료 상태·사용 가능한 별칭 추가를 하나의 DB 작업으로 반영한다.
- 기존 다른 문서의 별칭을 가져오지 않으며, 게시 완료 후 결과 문서로 이동한다.

### AI 통합안 생성과 검토

1. 초안 제목·별칭을 정규화해 기존 제목·슬러그·넘겨주기 별칭과 일치하는 문서를 추천한다. 하나만 일치하면 기본 선택하며, 이름이 달라도 같은 주제의 문서를 직접 선택할 수 있다.
2. AI가 기존 본문과 새 초안을 비교해 중복을 정리하고 상충하지 않는 기존 정보·출처·주의사항·위키 링크를 보존하도록 요청한다.
3. **상충하는 사실·수치에는 새 초안을 우선 적용**한다. 각 항목을 주제·기존 내용·새 초안 내용으로 별도 반환한다.
4. 통합안을 초안에 저장하며 이 단계에서 게시 문서는 변경하지 않는다.
5. 검토 화면에서 변경 요약, 상충 항목, 기존 본문과 AI 통합안의 차이, 수정 가능한 최종 본문·검토자 입력을 제공한다. 차이 보기는 AI 원안 기준이며 이후 수동 편집까지 실시간 비교하지는 않는다.
6. 사용자가 본문·상충 내용 확인에 체크하고 **“검토 완료 · 기존 문서에 통합”**을 눌러 적용한다. 다시 생성·통합안 버리기도 제공한다.

제목·별칭 일치는 후보 제안이며 본문 의미 유사도를 통한 자동 중복 판정은 아니다. AI가 상충 항목을 놓칠 수 있으므로 최종 검토를 생략하지 않는다. AI 통합안 생성에는 API 키가 필요하며 키가 없으면 자동 연결·문자열 이어붙이기로 대체하지 않는다.

현재 서버 한도는 두 입력의 제목·본문 합계 20만 자, 통합 본문 20만 자, 요약 2,000자, 상충 항목 30개, 항목별 주제·기존·새 내용 각각 3,000자다. 초안 수정 본문도 20만 자 이하로 제한한다.

### 통합 적용·역사·수정 충돌

- 최종 통합 본문의 콘텐츠 검사를 통과해야 적용한다. 기존 문서 ID·제목·주소는 유지하고 본문·편집자·수정 시각을 갱신한다.
- 본문 갱신·리비전 추가·초안 `published` 처리·사용 가능한 별칭 추가를 원자적으로 반영한다. 사용 가능한 경우 새 초안의 제목도 기존 문서의 별칭으로 연결한다.
- 역사에 **`[AI 통합 · 새 초안 우선]`** 표시, 초안 ID·제목·업로드 파일명·통합 요약·상충 건수·각 기존/새 내용을 기록한다.
- 검토자가 AI 본문을 추가 수정했으면 그 사실을 따로 남긴다. 최종 반영 내용은 저장된 리비전과 차이 보기에서 확인한다.
- 역사 화면은 AI 통합 항목을 별도 배지와 펼칠 수 있는 상세 기록으로 표시한다. 이전 리비전을 유지하고 본문 되돌리기도 제공한다.
- 초안·기존 문서 버전, 초안 내용 지문, 통합안 ID를 확인한다. 검토 중 기존 문서나 초안이 바뀌면 오래된 통합안을 적용하지 않고 새로 생성하도록 안내한다.
- 동시 적용 요청은 한 번만 반영한다. 초안의 수정·새 게시·삭제·통합안 버리기에도 버전 검사를 적용한다.
- 이 보호는 초안 처리·통합 경로의 범위다. 일반 문서 직접 편집까지 실시간 동시 편집이나 전면적인 충돌 해결을 제공하는 것은 아니다.

## 6. 콘텐츠 보호와 익명 편집

익명 이름은 `Editor-` 뒤 두 자리 이상의 숫자 또는 `Operator-` 뒤 대문자로 시작하는 영문 대문자·숫자·하이픈 형식을 사용한다. 예: `Editor-01`, `Editor-99`, `Operator-A`, `Operator-REVIEW`.

정규식 검사는 기밀·대외비, 인사·급여, 직원 식별 정보, 개인 연락처·이메일, 주민등록번호 등을 대상으로 한다. AI 의미 검사는 실명·개인 식별 정보·제한된 자료 여부를 보조 판단한다.

| 경로              | 현재 검사 범위                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------- |
| 업로드            | 추출 원문 정규식, 통과 시 원문 의미 검사, 생성 제목·본문 정규식. 실패 사유를 초안에 저장 |
| 초안 수정·새 게시 | 제목·본문 정규식 및 의미 검사                                                            |
| AI 통합안 생성    | 두 입력 및 생성 본문 정규식 검사                                                         |
| AI 통합 적용      | 대상 제목·최종 본문 정규식 및 의미 검사                                                  |
| AI 검색 설명      | 질문 및 근거 문서 제목·본문 정규식 검사, 답변 구조·출처 ID 검증                          |
| 직접 문서 편집    | 본문 정규식 검사                                                                         |
| 토론 등록         | 주제·본문 정규식 검사                                                                    |
| 역사 되돌리기     | 저장된 이전 본문 복원. 별도 콘텐츠 재검사 없음                                           |
| 시드              | 스크립트별 별도 검사. 업로드와 동일하다고 가정하지 않음                                  |

- 키가 없으면 의미 검사가 생략되며, 실제 의미 검사를 통과한 상태와 구분한다.
- 현행 업로드는 원문 검사에 실패해도 구조화 호출을 진행하고 차단된 초안을 남길 수 있다. 외부 AI 전송 전에 모든 민감 정보를 차단하는 구조로 설명하지 않는다.
- 익명 이름은 형식 검사이며 인증·권한 검증이 아니다. 자동 검사가 문서의 사실 정확성이나 게시 적합성을 보장하지는 않는다.

## 7. 우선 적용할 테마·디자인과 화면 개선 목표

**최종 디자인은 고딕체·읽기 중심 배치·중립적인 본문 면·일관된 작업 화면을 기준으로 한다.** 아래 항목은 구현할 목표이며 현재 코드가 모두 충족한다는 뜻은 아니다. 기존 기능·브랜드 정체성·모달의 스크롤과 닫기 동작을 보존하면서 시각 체계와 작업 동선을 개선한다.

- 베이지·오렌지·올리브는 브랜드를 구분하는 색으로 유지한다. 긴 본문과 입력 화면에는 라이트 모드의 밝고 중립적인 바탕, 다크 모드의 대응하는 중립 면과 충분한 대비를 사용한다.
- 문서 제목·본문 제목·검색·편집·초안·토론·이력은 **Figtree + IBM Plex Sans KR 등 기존 로컬 고딕체 중심**으로 통일한다. **Caprasimo와 Gowun Batang 등 장식용 글꼴은 로고와 짧은 소개에 한정**한다.
- 큰 홍보 카드, 과도한 빈 공간, 모든 영역을 둥근 카드로 나누는 구성보다 문서·검색 결과·검토 항목의 가독성과 정보 밀도를 우선한다.
- 기존 15px 본문, 38/27/19px 제목, 28px 패널 곡률, 1180px 공통 폭은 현재 구현값이다. 이를 모든 화면의 고정 목표로 강제하지 않으며 읽기 폭·글자 계층·컴포넌트별 토큰으로 정리한다.
- 브랜드 팔레트의 역할과 라이트·다크 대응을 유지한다. 중립적인 본문·입력 배경의 정확한 색과 여백은 긴 문서·검색·편집 화면의 가독성, 대비, 모바일 배치를 확인해 공통 토큰으로 확정한다.

### 7.1. 서비스 전체의 시각 체계 통일 — P0

- 홈의 베이지·오렌지·올리브 브랜드 색을 유지하되, 본문과 입력 화면은 중립적인 바탕과 충분한 대비를 사용한다.
- 고딕체·명확한 제목 계층·구분선을 검색·편집·초안·토론·이력 화면 전체에 적용한다. 장식용 글꼴은 로고와 짧은 소개에 한정한다.
- 색상, 글자 크기, 여백, 테두리, 모서리, 그림자, 화면 폭을 공통 토큰으로 정리한다. 유사한 카드와 버튼마다 다른 스타일이 생기지 않게 한다.
- 큰 홍보 카드와 과도한 여백을 줄이고 실제 검색 결과·문서·검토 항목의 정보 밀도를 높인다.
- 버튼은 주요 행동·보조 행동·위험 행동의 위계를 통일한다. 저장·게시·삭제를 같은 중요도로 배치하지 않는다.
- 빈 상태, 로딩, 오류, 성공, 비활성, 검토 대기 상태를 공통 컴포넌트로 제공한다. 오류 안내에는 사용자가 할 수 있는 다음 행동을 함께 표시한다.

### 7.2. 탐색 구조와 홈 — P0·P1

- 전역 메뉴를 **검색·문서 탐색·최근 변경·초안 검토** 중심으로 정리하고, 새 문서 작성과 파일 전환 진입점을 모든 주요 화면에서 찾을 수 있게 한다.
- 홈 첫 화면에는 검색창, 분야별 진입점, 최근 본 문서 또는 사용 안내를 배치한다. 전체 통계와 서비스 소개는 그 아래로 이동한다.
- 활동 보기에서는 검토할 초안, 최근 변경, 진행 중인 토론과 공지를 보여 주고, 각 항목에서 실제 작업 화면으로 바로 이동한다.
- 검색과 지식 지도는 같은 문서 데이터·분류를 사용한다. 선택한 보기와 필터는 URL에 남겨 공유·새로고침·뒤로 가기를 지원한다.
- 모바일에서는 긴 메뉴를 접고 검색과 현재 작업을 우선 배치한다. 숨겨진 메뉴도 키보드로 열고 닫을 수 있게 한다.
- 개인화 구현 전에는 최근 본 문서나 즐겨찾기를 가상 데이터로 채우지 않는다. 처음 방문한 사용자에게 실제 문서와 명확한 시작 안내를 제공한다.

### 7.3. 문서 읽기 고도화 — P0·P1

- 제목 수준에 맞춘 계층형 목차, 1·1.1·1.1.1 형태의 문단 번호, 큰 제목 아래의 얇은 구분선으로 긴 문서를 구성한다. 목차에서 해당 문단으로 이동하고 본문 폭과 한국어 줄바꿈을 긴 문서 기준으로 조정한다.
- 데스크톱에서는 긴 문서의 목차를 스크롤 중에도 접근 가능하게 하고 현재 읽는 문단을 표시한다. 모바일에서는 접이식 목차와 본문 복귀를 제공한다.
- 글자 크기와 읽기 폭을 선택하고 브라우저에 설정을 저장한다. 기본값만으로도 충분히 읽을 수 있게 한다.
- 문단 링크 복사, 각주에서 본문으로 돌아가기, 표의 가로 스크롤 안내, 코드 복사, 인쇄용 스타일을 추가한다.
- 현재 순번 기반 `section-N` 주소는 문단 삽입에 따라 달라질 수 있다. 문단 식별자와 리비전 기준 링크를 설계해 기존 주소 호환과 새 링크의 안정성을 함께 확보한다.
- 제목 아래에는 요약·분류·다른 이름을, 보조 영역에는 출처·담당자·마지막 검토일·최근 수정일을 구분해서 표시한다. 메타데이터가 없으면 미등록 상태를 표시한다.
- `검토 완료`, `검토 필요`, `예시 문서`, `보관됨`은 실제 기록에 따라 표시한다. 최근 편집됐다는 이유로 검토 완료라고 표시하지 않는다.
- 관련 문서와 역링크는 연결 이유를 구분한다. 모바일에서도 본문 아래에서 접근할 수 있게 한다.

### 7.4. 검색 결과와 AI 설명 — P0·P1

- 현재 자동 생성되는 AI 설명의 진입 방식을 개선한다. 일반 검색 결과를 먼저 제공하고, AI 설명은 사용자가 요청할 때 생성하는 흐름을 기본으로 한다. AI 응답을 기다리느라 원문 탐색이 늦어지지 않게 한다.
- 결과마다 제목, 분류, 검색어가 일치하는 본문 문단, 수정일과 검토 상태를 보여 준다. 본문 앞부분만 잘라 보여 주는 방식을 개선한다.
- 제목·정확한 별칭 일치를 우선하고, 약어·한글 표기·띄어쓰기 차이를 평가용 검색어로 검증한다.
- 분야·태그·문서 상태·수정 기간 필터, 관련도·최근 수정순 정렬, 페이지 이동을 서버 검색에 적용한다. 필터가 전체 검색 범위와 AI 설명의 근거 문서에 일관되게 반영되게 한다.
- 검색 결과가 없을 때 별칭·유사 제목·필터 초기화를 안내하고, 이어서 신규 작성이나 업로드로 연결한다.
- AI 출처를 문서뿐 아니라 근거 문단과 당시 리비전에 연결한다. 여러 문서가 상충하면 차이를 보여 주고 사람이 원문을 판단하게 한다.
- AI 로딩·취소·근거 부족·서비스 오류를 구분한다. 취소는 서버 요청에도 가능한 범위에서 전달하고, 중복 요청·재시도·비용을 제어한다.

### 7.5. 작성과 편집 — P0·P1

- Markdown 편집기와 실시간 미리보기를 제공한다. 넓은 화면은 나란히, 모바일은 탭으로 전환한다.
- 제목·목록·표·인용·링크 삽입 도구, `[[` 입력 시 문서 자동완성, 용어·업무 절차·FAQ 템플릿을 제공한다.
- 문서 제목·분류·태그·별칭과 본문을 구분하고, 변경 요약·저장 상태·미저장 상태를 한곳에서 확인하게 한다.
- 새로고침·이동 전에 미저장 내용을 안내하고 임시 복구를 지원한다. 본문을 브라우저 저장소에 보관하는 경우 보관 기간·삭제 방법을 정하며, 민감 문서는 서버 임시 저장 정책을 따른다.
- 저장 전 변경 내용을 비교한다. 다른 사람이 먼저 저장했으면 조용히 덮어쓰지 않고 최신 버전과 내 변경을 함께 보여 준다.
- 문서가 아닌 일부 문단만 고치는 진입점도 제공하되, 같은 리비전 충돌 검사를 적용한다.
- 저장 실패 시 입력을 유지하고 문제 필드에 안내한다. 별칭 중복이나 제목 충돌 때문에 작성 내용을 다시 입력하지 않게 한다.

### 7.6. 업로드와 초안 검토 작업 공간 — P0·P1

- 업로드 전에 지원 형식·크기·텍스트 추출 한계와 파일 정보를 보여 준다. 기존 10MB·최대 8개 초안 기준을 유지한다.
- 수신·텍스트 추출·콘텐츠 검사·초안 생성·저장을 실제 처리 상태로 표시한다. 근거 없는 진행률이나 완료 시간을 만들지 않는다.
- 작업 식별자로 처리 결과를 다시 찾게 하고 중복 제출을 막는다. 브라우저 요청 종료와 서버 작업 취소를 같은 의미로 안내하지 않는다.
- 검토 화면은 **초안 목록·편집/미리보기·원문 근거**를 한 작업 공간에 배치한다. 모바일에서는 영역을 탭으로 전환한다.
- 검사 사유를 수정 대상 문장과 연결하고, 검사 완료·일부 검사 생략·검사 실패를 구별한다. AI 키가 없어서 의미 검사를 생략한 경우에도 명확히 표시한다.
- 같은 파일에서 생성한 초안을 명시적인 업로드 묶음 ID로 연결한다. 현재 파일명과 생성 시각 비교에 의존하는 묶음 판별을 대체한다.
- 중복 문서 후보, 출처 누락, 미작성 링크, 검토 필요 표시를 게시 전에 확인한다. 여러 초안은 각각의 검토 상태를 확인한 뒤 선택 게시한다.
- 원문은 우선 추출 텍스트와 파일명으로 대조한다. 페이지·시트·슬라이드·절 위치는 파서가 실제 확보한 경우에만 표시하며, 찾지 못한 위치를 AI가 만들어 내지 않게 한다.
- 현재 제공하는 AI 통합 후보·기존/새 상충 내용·수정 가능한 최종 본문·역사 기록을 새 검토 작업 공간에 포함한다. UI 재구성 때문에 통합 기능을 제거하거나 P2로 미루지 않는다.

### 7.7. 토론·이력·지식 지도 — P1·P2

- 토론에 답글, 진행 중·해결됨 상태, 대상 문단 연결을 추가한다. 해결된 제안에서 실제 수정 리비전으로 이동한다.
- P1에서는 두 본문 버전을 선택하고 추가·삭제·변경 내용을 구분한다. P2에서는 제목·별칭·분류 등 메타데이터 변경도 비교한다.
- 되돌리기 전에 적용될 차이를 보여 주고, 되돌림 자체도 새 리비전으로 남긴다.
- 지식 지도는 고정된 소수 노드 화면에서 선택 문서 중심 탐색으로 확장한다. 인접 문서·분야 필터와 연결 이유를 제공하고, 노드 수를 제한해 읽을 수 있는 화면을 유지한다.
- 지도와 같은 내용을 목록으로도 제공한다. 그래프 조작이 어려운 모바일이나 보조 기술 사용자도 연결된 지식을 탐색할 수 있게 한다.

### 7.9. 반응형·접근성·모달의 보존 조건

- 라이트·다크 전환과 `localStorage['wiki-theme']` 저장, 최초 테마 적용과 저장소 접근 실패 처리를 유지한다.
- 기존 1050px·800px·540px 분기와 로컬 WOFF2 자산을 출발점으로 삼는다. 목표 화면은 360px·768px·1440px에서도 검증하며 필요한 배치 조정은 허용한다.
- 데스크톱의 본문·보조 영역은 읽기 폭을 중심으로 정리하고 작은 화면에서는 검색·목차·현재 작업을 먼저 배치한다. 관련 문서·역링크는 모바일에서 영구적으로 숨기기보다 본문 아래로 재배치한다.
- 표·코드 내부의 가로 스크롤을 제외하고 페이지 전체의 가로 넘침을 막는다. 긴 제목·별칭·상충 내용도 화면 밖으로 밀리지 않게 한다.
- 주 행동·보조 행동·위험 행동을 구분하고, 입력 레이블·초점·처리 상태·오류·다음 행동을 일관되게 표시한다. 200% 확대·키보드 사용·`prefers-reduced-motion`에 대응한다.
- 차이 보기의 추가는 올리브, 삭제·변경 전은 오렌지 계열과 취소선으로 표현한다. AI 표시·출처 링크·통합 상충 항목과 이력 배지는 유지하되 색만으로 의미를 전달하지 않는다.
- **모달 내부 스크롤·항상 보이는 X·배경 스크롤 차단**은 디자인 개선 후에도 유지한다. 둥근 모서리 밖으로 스크롤바가 나오거나 본문과 X가 함께 스크롤되는 상태로 돌아가지 않는다.

## 8. 데이터 모델·예시 문서·운영

### 저장 구조와 보존할 제약

모든 테이블의 `id`는 `BIGSERIAL PRIMARY KEY`다. 시각은 `TIMESTAMPTZ`로 저장하고 생성·수정 시각의 초기값은 현재 시각이다. 아래 필드는 별도 설명이 없는 한 필수 값이다. 기존 행의 ID와 문서·리비전·별칭·초안·토론의 연결을 보존한다.

| 테이블          | 필드·제약·의미                                                                                                                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `documents`     | `slug TEXT UNIQUE`, `title TEXT UNIQUE`, `content TEXT DEFAULT ''`, `editor_handle TEXT DEFAULT 'Editor-01'`, `created_at`, `updated_at`. 현재 게시된 Markdown 본문과 대표 주소를 저장한다.                                                                                                 |
| `revisions`     | `document_id BIGINT`, `content TEXT`, `editor_handle TEXT`, `summary TEXT DEFAULT ''`, `created_at`. 문서별 본문 버전이며 AI 통합 상세도 변경 요약에 기록한다.                                                                                                                              |
| `redirects`     | `alias_slug TEXT UNIQUE`, `alias_title TEXT`, `document_id BIGINT`. 별칭 주소를 하나의 대표 문서에 연결한다.                                                                                                                                                                                |
| `drafts`        | `title TEXT`, `slug TEXT`, `content TEXT`, 선택 값 `source_name TEXT`, `aliases JSONB DEFAULT []`, `governance JSONB DEFAULT {}`, `status TEXT DEFAULT 'review'`, `editor_handle TEXT DEFAULT 'Editor-01'`, `created_at`, `updated_at`. 상태는 `review`, `blocked`, `published`로 제한한다. |
| `discussions`   | `document_id BIGINT`, `thread_title TEXT`, `body TEXT`, `editor_handle TEXT`, `created_at`. 문서별 토론 주제와 의견을 저장한다.                                                                                                                                                             |
| `announcements` | `title TEXT`, `body TEXT DEFAULT ''`, `created_at`. 공지 제목과 본문을 저장한다.                                                                                                                                                                                                            |

- 리비전·별칭·토론의 `document_id`는 문서 외래 키이며 현재 물리 삭제 시 연쇄 삭제된다. 휴지통 도입 후 사용자 삭제는 우선 보관 상태 전환으로 처리해 이 관계를 복원 가능하게 유지한다.
- 기존 조회 인덱스는 리비전과 토론의 문서 ID·생성 시각 내림차순, 문서 수정 시각 내림차순, 소문자 변환 제목, 초안 상태·생성 시각 내림차순이다.
- 제목과 대표 슬러그의 고유성뿐 아니라 별칭 주소와의 충돌도 서버에서 검사한다. 다른 문서의 별칭을 암묵적으로 이전하지 않는다.
- XLSX/PPTX 추출과 현행 초안 AI 통합은 이 저장 구조에서 동작한다. 추가 메타데이터·출처 구간·작업 상태·전체 상태 이력은 기존 데이터를 보존하는 마이그레이션으로 확장한다.

### 초안 AI 통합의 저장 계약

AI 통합안은 `drafts.governance.merge`에 저장한다. 통합안 생성만으로 게시 문서나 리비전을 변경하지 않는다.

- 고유 통합안 ID, 대상 문서 ID·제목·슬러그, 대상 문서의 정확한 수정 버전, 비교에 사용한 기존 본문, 통합 본문, 요약과 상충 목록을 저장한다.
- 대상 버전은 DB의 `updated_at::text`를 사용해 비교 정밀도를 유지한다.
- 초안 지문은 제목·슬러그·본문·별칭·업로드 자료명·편집자를 포함한 SHA-256 값이다. 검토 중 이 값이 바뀌면 통합안을 다시 생성한다.
- 상충 목록의 각 항목은 주제 `topic`, 기존 내용 `previous`, 새 초안 내용 `incoming`을 가진다.
- 적용 시 초안과 대상 문서를 잠그고 버전·통합안 ID·초안 지문을 다시 확인한다. 본문·리비전·사용 가능한 별칭·초안 게시 상태를 하나의 트랜잭션으로 반영한다.
- 적용 후 `mergedInto`에 대상 연결을 남긴다. 역사에는 새 초안 우선 정책, 자료명, 통합 요약, 기존/새 상충 내용, 검토자의 추가 수정 여부를 보존한다.

다음은 검색·별칭·문서 연결·미게시 초안 안내를 확인하기 위한 예시다. **승인된 현장 운전 기준이나 업무 절차로 안내하지 않는다.** 아래 핵심 내용은 데이터의 의미를 정의하며, 이미 저장된 본문을 이 요약으로 축약하거나 사용자 편집을 덮어쓰지 않는다.

- 예시 적재는 같은 제목·슬러그·별칭이 있으면 건너뛰고 반복 실행을 직렬화한다. 사용자 편집과 기존 초안을 덮어쓰거나 중복 생성하지 않는다.
- 사용자가 예시를 편집·게시한 뒤에는 초기 상태로 되돌리지 않는다. 문서 ID나 전체 문서 수를 화면에 하드코딩하지 않는다.

### 개발 환경과 실행 절차

Bun, Node.js 22와 PostgreSQL/Neon 연결을 준비한다. 서버 환경 변수는 다음 의미로 설정한다. 실제 비밀 값은 문서나 클라이언트에 넣지 않는다.

| 환경 변수        | 설정 기준                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DATABASE_URL`   | 필수. 사용할 PostgreSQL/Neon DB의 연결 문자열. 검증 환경은 사용자 자료와 분리한다.                                                               |
| `OPENAI_API_KEY` | AI 답변·용어별 생성·의미 검사·AI 통합에 사용한다. 없으면 일반 검색·수동 작성과 추출 텍스트 기반 기본 초안 한 개를 제공하고 검사 생략을 표시한다. |
| `OPENAI_MODEL`   | 선택. 설정하지 않으면 `gpt-5-mini`를 사용한다.                                                                                                   |

1. `bun install`로 기존 의존성을 설치한다.
2. 대상 DB와 서버 환경 변수를 확인한 뒤 `bun run migrate`로 저장 구조를 준비한다.
3. 초기 데이터가 필요한 환경에만 아래 적재 명령을 실행한다. 기존 데이터가 있는 환경에서 일반 시드를 무조건 반복하지 않는다.
4. `bun run dev`로 개발 서버를 실행하고 출력된 주소에서 확인한다.
5. 기능 변경 후 `bun run test`, `bun run check`, `bun run build`를 실행한다. `bun run preview`는 빌드 결과를 로컬에서 확인하는 용도이며 실제 서버리스 배포 검증과 구분한다.

| 명령                     | 실제 동작과 반복 실행 조건                                                                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun run migrate`        | 기본 테이블·제약·인덱스를 준비한다. 향후 스키마 확장에는 적용 이력·순차 실행·기존 데이터 보충·복구 절차를 추가한다.                                                                                      |
| `bun run seed`           | 기본 정책·도움말 문서와 공지를 준비하고 초기 DOCX/PDF 자료를 파일당 한 초안으로 처리한다. 기본 문서를 갱신하거나 반복 실행 시 파일 초안을 추가할 수 있다. 웹 업로드의 네 형식·다중 초안 생성과 구분한다. |
| `bun run seed:demo`      | 기능 확인용 일반 데모 문서를 준비한다. 일곱 업무 예시의 보존형 적재와 다른 명령이며 동일한 중복 방지를 가정하지 않는다.                                                                                  |
| `bun run seed:prototype` | 위 표의 일곱 업무 예시를 제목·슬러그·별칭 충돌 확인과 반복 실행 직렬화를 거쳐 보존형으로 적재한다. 기존 행과 사용자 편집은 유지한다.                                                                     |

### 배포와 빌드 판정

- Vercel의 Framework Preset은 SvelteKit, 서버 Node.js 버전은 22.x로 설정한다.
- 설치 명령은 `bun install --frozen-lockfile`, 빌드 명령은 `bun run build`, 출력 디렉터리는 어댑터 기본값을 사용한다.
- 배포 환경에도 `DATABASE_URL`을 설정하고 필요한 AI 환경 변수를 설정한다. DB 마이그레이션과 필요한 초기 데이터 적재는 배포 전 별도 단계로 실행하며 빌드 중 자동 실행하지 않는다.
- 실제 사내 운영 전에 서버 세션과 권한 검사를 적용한다. 익명 편집자 입력만 있는 상태를 운영 준비 완료로 표시하지 않는다.
- Windows에서는 Vercel 패키징의 심볼릭 링크 생성 권한 부족으로 앱 컴파일 후 `EPERM`이 발생할 수 있다. 적절한 OS 권한 또는 지원되는 빌드 환경에서 검증하고, 컴파일 성공·패키징 성공·실제 배포 성공을 따로 보고한다. 우회 방식으로 확인한 결과를 기본 빌드 명령의 성공으로 기록하지 않는다.

## 9. 검증 시나리오와 회귀 확인 항목

현재 동작의 보존과 개선 목표의 충족을 함께 확인한다. 의도적으로 개선한 동작은 새 요구로 검증하며, 영구 삭제·저장된 본문만 미리보기·자동 AI 호출 같은 현행 제약을 회귀 기준으로 고정하지 않는다.

### 자동 검사와 실제 연동 검증

- `bun run test`로 링크·별칭 해석, 검색어 정리, 여러 초안의 출력 구조, 한국어 용어 연결, AI 출처 ID, 파일 파싱, 통합 후보·상충 이력·게시 보호를 검증한다.
- `bun run check`로 Svelte·JavaScript 진단을 확인하고, `bun run build`로 앱 컴파일과 배포 패키징을 확인한다.
- DB 통합 검증은 기본적으로 생략될 수 있다. 검증용 DB의 `DATABASE_URL`과 `RUN_MERGE_DB_TESTS=1`을 프로세스 환경 변수로 설정한 뒤 `bun run test`를 실행한다. DB 검증을 건너뛴 결과를 통과로 기록하지 않는다.
- DB에서는 새 게시 중복 방지, 제목·슬러그·별칭 충돌, 오래된 초안·통합안 차단, 동시 적용 단 한 번 반영, 중간 실패 시 전체 롤백을 확인한다.
- AI 모의 응답 검증과 실제 OpenAI 호출 검증을 구분한다. 실제 호출에서는 여러 게시 문서 기반 답변과 출처, DOCX/PDF/XLSX/PPTX의 초안 생성, 의미 검사, 수정·게시·리비전 기록을 확인한다.
- 실제 연동이 불가능한 항목은 사용 불가 원인과 미확인 범위를 기록한다. 모의 결과를 실제 AI·DB 검증으로 표시하지 않는다.
- 검증 자료는 고유한 제목·업로드 이름·생성 ID로 식별하고 생성한 레코드만 정리한다. 실제 사용자 자료와 보존 대상 예시를 정리 대상으로 삼지 않는다.

### AI 통합의 구체적인 확인 사례

1. 기존 문서에 “점검 주기 7일”과 “파란 보관함에 보관”을 넣고, 같은 주제의 새 초안에는 “점검 주기 3일”을 넣는다.
2. 통합안을 생성하면 점검 주기의 기존 값 7일과 새 값 3일이 상충 항목으로 표시되어야 한다. 통합 본문은 3일을 사용하고 별도 보관 정보는 유지해야 한다.
3. 생성·검토·재생성만으로 기존 문서 본문이나 리비전이 바뀌면 안 된다.
4. 검토자가 최종 본문을 수정하고 검토 확인 후 적용하면 최종 입력 내용이 저장되고 대상 문서로 이동해야 한다.
5. 문서 ID·제목·주소와 이전 리비전을 유지하며 역사에 새 초안 우선 정책, 기존/새 상충 값, 초안·자료 정보, 검토자의 추가 수정 여부를 남겨야 한다.
6. 검토 도중 기존 문서 또는 초안이 변경되면 적용을 막고 재생성을 안내해야 한다. 동시 적용·반복 요청에서도 리비전과 별칭이 중복 반영되면 안 된다.
7. 새 문서 게시와 통합 중 실패하면 문서·리비전·별칭·초안 상태가 일부만 반영되지 않아야 한다.

## 11. 데이터·AI·운영의 개선 설계 기준

아래는 추가로 설계·구현할 기준이다. 현재의 문서·리비전·별칭·초안·토론·공지 데이터와 경로별 검사 동작을 출발점으로 삼고, 확장 적용 전까지 완료된 기능으로 설명하지 않는다.

### 11.1. 점진적 데이터 확장

- `documents`에 요약·분류·문서 상태·검토 정보·보관 상태를 단계적으로 추가한다. 여러 값이 필요한 태그와 읽기 묶음은 관계 테이블로 관리한다.
- 이미 저장한 AI 통합의 상충 상세·새 초안 우선 정책을 보존하면서 `revisions`를 본문 중심에서 제목·별칭·메타데이터를 포함한 문서 상태 기록으로 확장한다. 과거에 기록하지 않은 값은 복원 가능한 것처럼 표시하지 않는다.
- 업로드 묶음, 추출 원문 구간, 초안과 출처 연결, 작업 상태를 명시적으로 저장한다. 초안 검토 상태와 변환 작업 상태는 별도로 관리한다.
- 브라우저 내 개인화는 P1에서 제공하고, 동일 계정의 기기 간 동기화·구독·알림은 계정 도입 후 사용자 관계 테이블로 확장한다. 익명 이름만으로 타인의 개인 목록에 접근하지 않게 한다.
- 마이그레이션 실행기에 적용 이력과 순차 실행을 추가한다. 기존 데이터 보충과 실패 시 복구 절차를 포함한다.

### 11.2. 검색·성능

- 목록 화면은 필요한 요약과 개수만 조회한다. 페이지 크기를 제한하고 홈·문서·초안·이력에서 전체 본문을 불필요하게 읽지 않는다.
- 서버에서 필터·정렬·페이지 처리를 수행하며 정확한 별칭 조회를 우선한다. 한국어 검색 품질은 실제 업무 용어로 평가한다.
- SQL 실행 계획과 실제 지연을 측정한 후 인덱스를 추가한다. 부분 일치 개선이 필요하면 PostgreSQL 확장 사용 가능 여부와 효과를 검증한 뒤 도입한다.
- 그래프와 역링크는 변경 시 갱신하는 관계 데이터 또는 제한된 조회로 전환한다. 모든 페이지 요청마다 전체 문서 그래프를 재계산하지 않게 한다.
- AI 답변을 캐시하는 경우 검색어·필터·근거 문서 리비전·접근 범위를 키에 반영하고, 수정·보관·권한 변경 때 무효화한다.

### 11.3. AI와 콘텐츠 보호

- AI는 초안·요약·링크 후보·검토 보조를 제공한다. 게시, 문서 병합, 사실 승인에는 사람의 명시적 판단이 필요하다.
- 업로드 원문·검색어·근거 문서에 공통 전송 전 검사를 적용한다. 검사 실패 시 의미 검사와 구조화 등 후속 외부 호출로 넘어가지 않게 한다.
- 직접 편집·초안 게시·되돌리기·토론에 검사 대상과 실패 처리를 일관되게 정의한다. 제목·별칭 등 노출되는 필드도 포함한다.
- 의미 검사 생략은 통과와 구분한다. API 키가 없어도 원문 기반 초안 작성과 수동 검토는 가능하게 하되, 운영 환경의 게시 조건은 별도로 적용한다.
- 프롬프트와 모델이 제안한 내용은 근거 자료와 비교할 수 있어야 한다. AI 출처 ID 검증만으로 사실 검증까지 완료됐다고 표시하지 않는다.
- 요청 제한, 최대 입력 크기, 중복 방지, 시간 제한과 오류 분류를 둔다. 운영 지표에는 필요한 처리 시간·성공 여부·사용량만 남기고 원문과 비밀 값은 기록하지 않는다.

### 11.4. 배포와 작업 처리

- 기존 단일 요청 변환 흐름부터 상태 조회·재시도·중복 방지를 개선한다. 작업 상태를 DB에 저장하는 것만으로 백그라운드 실행이 보장된다고 가정하지 않는다.
- 서버리스 실행 시간과 업로드 한도는 실제 배포 설정에서 확인한다. 화면에 안내한 제한과 배포 환경의 제한이 다르면 일치시키거나 지원 범위를 조정한다.
- 지속 실행이 필요한 비동기 변환·여러 파일 일괄 처리는 별도 후속 단계다. 실행 수단과 재개·실패 복구를 검증하기 전에는 새 큐나 워커를 기본 인프라로 추가하지 않는다.
- 일반 DB 오류·AI 장애·지원하지 않는 파일을 구별하고, 내부 오류나 연결 정보를 사용자에게 그대로 노출하지 않는다.
- 인증·권한은 화면 숨김만으로 구현하지 않는다. 서버 조회·검색·AI 근거 선택·다운로드·변경 API 모두에 적용한다.

## 12. 실행 순서와 단계별 완료 기준

각 단계는 직전 단계의 핵심 흐름 검증을 마친 뒤 진행한다. 계정 기반 기능은 인증·권한 작업 완료 후 활성화한다. P2까지 운영을 미룬다는 뜻은 아니며 실제 사내 운영 일정이 앞서면 기본 인증·권한을 먼저 수행한다.

현재 완료되어 모든 단계에서 유지할 기능은 다음과 같다. 이는 P0 전체 완료를 뜻하지 않는다.

- [x] 초안 새 게시·AI 통합에서 문서·리비전·별칭·초안 상태를 원자적으로 반영한다.
- [x] 같은 제목·슬러그·별칭의 새 게시로 기존 문서를 덮어쓰지 않는다.
- [x] AI 통합안을 검토한 뒤 새 초안 우선 적용, 상충 상세 역사 기록, 이전 리비전 보존을 제공한다.
- [x] 초안·대상 문서 변경과 동시 적용 요청을 확인해 오래된 통합·중복 적용을 막는다.
- [x] DOCX/PDF/XLSX/PPTX, 용어별 초안 1–8개, 모달 내부 스크롤과 고정 닫기 버튼을 제공한다.

### P0. 일관된 UI와 안심하고 저장하는 기본 흐름

## 14. 현재 한계와 이번 개선의 범위 밖

### 14.1. 현재 한계 — 개선 목표와 구분

- 현재 로그인·계정·역할별 권한은 없다. 기본 인증·권한은 실제 사내 운영 전 필수이며 P2의 계정 기반 기능보다 먼저 완료해야 한다.
- 직접 편집은 본문, 토론은 주제·본문만 정규식으로 검사하며 되돌리기에는 재검사가 없다. 업로드 검사 실패 후 구조화 호출이 이어질 수도 있다. 공통 전송 전 차단과 노출 필드·게시 경로 전체의 일관된 검사는 P0 목표다.
- 초안 통합 후보는 제목·별칭 일치 기준이며 본문 의미 유사도로 자동 판정하지 않는다. 일반 직접 편집은 초안 통합과 동일한 충돌 보호가 없고, 별칭 충돌 시 연결 갱신·입력에서 지운 별칭 미삭제 문제가 남아 있다.
- 되돌리기는 본문 중심이며 제목·별칭·초안 게시 상태 전체를 복원하지 않는다. 현재 되돌리기 편집자 표시는 `Operator-A`다.
- 문서 삭제는 현재 영구 삭제이고 휴지통은 미구현이다. 휴지통을 P0에 도입하기 전에는 복구 가능하다고 안내하지 않는다.
- 원문 대조 작업 공간·작업 재조회·중복 업로드 방지·실시간 편집 미리보기·임시 복구·즐겨찾기·최근 본 문서·검토 주기·토론 답글·앱 내 알림은 추가 목표다.
- 현재 AI 스트리밍·검색 캐시·사용자별 방문 이력·조회수 집계는 없다. 홈·문서 관계 계산은 게시 문서를 읽어 수행하므로 대규모 데이터 성능을 검증한 것으로 보지 않는다.
- 현재 공지 작성 전용 UI는 없다. 서식·차트·업로드 자료의 레이아웃·Excel 재계산·발표자 노트도 지원하지 않는다.

### 14.2. 이번 개선의 범위 밖

- 프런트엔드·백엔드 프레임워크 교체와 전체 재작성, 전면 TypeScript 전환.
- 실시간 다중 사용자 공동 편집, CRDT, 자동 충돌 병합.
- 별도 벡터 DB·검색 서버 도입과 범용 대화형 챗봇.
- 스캔 PDF·이미지 OCR, 업로드 자료의 시각적 레이아웃 재현, 구형 Office 형식 지원.
- AI 자동 게시·무검토 자동 병합·근거 없는 사실 보완. 현재의 **사람이 검토한 초안→기존 문서 AI 통합**은 계속 제공한다.
- 외부 메신저·이메일 알림, 조직별 SSO, 복잡한 부서 권한, 다중 조직 서비스. 기본 계정·역할 도입과 구분한다.
- 검증되지 않은 대용량 업로드 파일 영구 보관, 무제한 일괄 변환, 실행 수단이 없는 큐·워커의 기본 인프라 도입.

새 기능은 **필요한 지식을 더 빨리 찾는가, 내용을 더 쉽게 이해·검증하는가, 수정과 검토를 더 안전하게 끝내는가**를 기준으로 우선순위를 정한다. 제품 개선 시 현재 기능 보존 기준과 디자인 목표의 적용 상태, 마이그레이션·검증 기록을 함께 갱신한다.

## 15. 완료 판정과 결과 보고

구현 결과는 이 문서의 요구와 직접 대조해 판정한다. 화면만 구현하고 저장·검색·검사·접근 제어가 연결되지 않은 상태를 완료로 표시하지 않는다.

- P0·P1·P2의 체크 항목별로 완료·미완료·검증 불가를 구분하고 남은 의존 조건을 명시한다.
- 기존 핵심 기능, 새 디자인, 데이터 보존과 마이그레이션, 오류·복구 흐름의 검증 결과를 기록한다.
- 자동 검사에는 실행 명령과 성공·실패·생략 결과를, 화면 검사에는 화면 크기·테마·확인한 사용자 흐름을 남긴다.
- AI·DB 검증에는 실제 연동 여부, 입력 사례, 기대 결과와 실제 결과를 남긴다. 비밀 키·접속 문자열·민감 본문은 기록하지 않는다.
- 성능·사용성 목표는 측정 환경·데이터 규모·실제 측정값을 함께 보고한다. 측정하지 않은 목표를 달성했다고 쓰지 않는다.
- 동작 변경과 남은 한계를 사용자 관점에서 설명한다. 환경 때문에 확인할 수 없는 항목은 구현 완료와 검증 미완료를 구분한다.

최종적으로 구성원이 필요한 지식을 찾고 읽으며, 문서를 작성·비교·검토·게시하고, 잘못된 변경에서 복구하는 전체 흐름이 일관된 화면과 보존 가능한 데이터 위에서 동작해야 한다.
